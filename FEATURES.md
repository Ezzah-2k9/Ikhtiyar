# Ikhtiyar mobility feature update

This update adds weather advisories, an optional live-traffic map layer, conservative Metro availability, persistent monthly CO₂-saving goals, saved destinations, and gamification. The changes are compatible with the existing Flask app and both SQLite and PostgreSQL.

## What changed

- **Weather advisories:** Current destination conditions can trigger heat, rain, thunderstorm, wind, and low-visibility guidance. Open-Meteo is the no-key provider; OpenWeather is an optional fallback. The guidance is threshold-based and is explicitly not an official UAE emergency alert. When live weather is unavailable, the page says so rather than displaying a false all-clear.
- **Traffic map:** The calculator has a redesigned route/conditions panel, Show/Hide traffic control, and a green-to-red legend. TomTom flow tiles are requested through an authenticated Flask endpoint so the API key is not placed in browser JavaScript. If TomTom rejects the key or the request quota is reached, the calculator reports a safe status category and the Render logs record only the provider's HTTP status. Traffic colors are shown only when real tiles load; the app does not invent traffic data.
- **Transit availability:** A Metro option is shown only when the trip is at least 2 km and both endpoints are within 1.25 km of mapped active Dubai Metro stations. This station-proximity test does not check a live route, transfers, operating hours, or a timetable. Bus and Metro time/fare figures remain labelled estimates.
- **Route accuracy:** Configured OpenRouteService, Geoapify, or TomTom road routes are preferred. If none return a road route, the app can request a driving route from the public OSRM demo; walking/cycling remain estimates unless a configured provider supports them. If the demo is unavailable, the map draws a dashed approximate direction rather than presenting it as street navigation. OSRM's demo is for reasonable non-commercial use, asks clients not to exceed one request per second, and provides no uptime guarantee.
- **Monthly goals:** Set one cumulative monthly CO₂-saving target in Settings → Preferences. Recorded trips add their positive CO₂ savings relative to the driving baseline; a fast trip is still selectable and does not erase savings from other trips. When progress is behind the month's pace, the recommendation leans toward lower-emission options but still shows every option. The dashboard displays progress and reports the previous month's result after the month ends. Trips do not count if trip-history saving is disabled.
- **Saved destinations:** Save a place with a personal label such as Home or Office. The resolved coordinates are retained, so the saved place can be reused as either route endpoint without geocoding it again. Up to 25 places may be saved per account.
- **Gamification:** Each recorded trip earns XP; eligible sustainable trips earn more, the first saved trip of a day earns a daily bonus, and consecutive trip days build a streak. Levels advance every 100 XP. The dashboard shows three weekly challenges, progress bars, and rewards. Challenge rewards are persisted and cannot be claimed repeatedly for the same week. Each calculation also issues short-lived signed route quotes; one transport option can be recorded per calculation, and client-edited costs/emissions are ignored.

## Render keys and data behavior

No API key is needed for weather advisories. Add a valid `TOMTOM_KEY` in the Render Environment settings to enable traffic tiles; the same key can also be used for road routes. If the overlay fails, check the safe HTTP status shown in the calculator and the matching Render service log entry: 401/403 points to the key or product access, 429 to quota/rate limits, and 5xx to the provider/service. `ORS_KEY` and `GEOAPIFY_KEY` are alternative routing providers. `LOCATIONIQ_KEY` is recommended for precise private/street-address geocoding. Without it, public OpenStreetMap Nominatim is queried only after a user submits a general landmark search; requests are cached and rate-limited to roughly one per second. The address detector blocks common patterns but is best-effort, not a privacy guarantee. Do not submit private locations without a trusted provider configured. Public geocoding may be unavailable or rate-limited; configure a trusted provider for consistent lookup.

The new tables for saved coordinates, streak/XP state, weekly challenge rewards, one-use route quote claims, and month-by-month targets are created automatically on app startup. New trip dates use Asia/Dubai local time. On Render, the retention of these records depends on the connected PostgreSQL plan; a Free Postgres database is temporary and expires under Render's policy.

## Quick manual verification

1. Sign in, set a monthly CO₂-saving target in Preferences, and compare a route. Confirm the calculator uses saved preferences or monthly progress for its recommendation while keeping all available modes visible.
2. Search a Dubai Metro-area trip and a trip with an endpoint well outside Dubai Metro coverage. Metro should only appear in the former case; its fare and time should still be identified as estimates.
3. Review the destination weather card. For a heat/rain/wind advisory, the message should show the weather source and an advisory disclaimer. If the provider is unavailable, the UI must say that live weather is unavailable.
4. Add a valid `TOMTOM_KEY` in Render and redeploy, then toggle the traffic layer. Confirm live colored tiles load. If not, use the safe HTTP status on the page and Render log to distinguish access, key, quota, or provider failures; a legend alone is not evidence that traffic loaded.
5. Save a destination as Home, use it as an origin and then as a destination, record a trip, and check that its positive CO₂ savings update the monthly total. The dashboard should show monthly progress, XP, streak, level progress, and weekly challenge rewards.
